# BE-35 — Phase 1: giám sát job và dung lượng lưu trữ (Claude, 22/10/2026)

Chỉ đọc: không sửa code, không migration, không đổi Contract / OpenAPI. Số liệu đo trên `luxmap_dev` và container dev, không
chạm `luxmap-prod`. Mục tiêu task list: **"Biết được job nào lỗi, còn bao nhiêu dung lượng"**.

## 1. Hiện trạng — cái gì đã có, cái gì thiếu

### 1.1 Job nền theo lịch (BE-26)

`scheduled_job` có đúng hai job (`node_offline`, `work_order_overdue`). Lược đồ thật:

```text
$ docker exec luxmap_postgres psql -U luxmap -d luxmap_dev -c "\d scheduled_job"
 job_name | text | not null        last_finished_at | timestamptz
 next_run_at | timestamptz | not null   last_error | text
 lease_token | uuid               run_count | bigint | not null
 lease_expires_at | timestamptz    last_started_at | timestamptz
Check constraints: ck_scheduled_job_last_error_length (≤ 1000), ck_scheduled_job_lease_together,
                   ck_scheduled_job_name, ck_scheduled_job_run_count

      job_name      |          next_run_at          |       last_finished_at        | last_error | run_count
 node_offline       | 2026-10-17 14:08:21.80679+00  | 2026-10-17 14:07:21.80679+00  |            |         9
 work_order_overdue | 2026-10-17 14:19:21.702459+00 | 2026-10-17 14:04:21.702459+00 |            |         4
```

Ba lỗ hổng, đọc từ `ScheduledJobRunner.FinishAsync`:

- **Lỗi bị xoá ở lần chạy thành công kế tiếp** (`last_error = $4`, `$4 = NULL` khi thành công). Job lỗi chập chờn (lỗi, đúng, lỗi…)
  nhìn từ ngoài gần như lúc nào cũng "ổn".
- **Không đếm lần lỗi.** `run_count` chỉ tăng khi thành công; không có `last_failed_at`, không có số lần lỗi liên tiếp.
- **Job bị bỏ đói không có dấu hiệu.** Dòng trên `luxmap_dev` có `next_run_at` = 17/10, tức **đã quá hạn 5 ngày** — API dev không
  chạy từ hôm đó. Trên production, cùng hình dạng đó nghĩa là worker chết hoặc instance chạy `Jobs:Enabled=false`. Tính được từ dữ liệu
  sẵn có: `next_run_at < now() − ngưỡng` và lease trống.

### 1.2 Xử lý sweep (`SurveyProcessingWorker`)

Không đi qua `scheduled_job` — có hàng đợi riêng trên `survey_sweep` (`processing_status`, `processing_lease_*`, `processing_attempt`,
`MaxAttempts = 3`) và mỗi lần chạy một dòng `survey_processing_run` (`result_state IN ('succeeded','failed')`, `error_code` bắt buộc khi
`failed` — `ck_survey_run_state`). Hơn 30 mã lỗi (31 mã khác nhau chỉ riêng qua `new ProcessingFailure(…)`; `VIDEO_TIMEOUT`, `VIDEO_OUTPUT_LIMIT`, `VIDEO_DEVICE_MAPPING_PENDING`, `RETRY_EXHAUSTED`,
`VIDEO_TEMP_QUOTA`…). Tức dữ liệu để biết "sweep nào lỗi, vì sao" **đã đủ**; chỉ thiếu chỗ xem tổng hợp. Quản lý đã xem từng sweep qua
BE-17; Quản trị hệ thống không có cái nhìn toàn hệ thống.

`luxmap_dev` hiện 0 sweep, 0 run (`GROUP BY` trả 0 dòng) — test Phase 2 phải tự trồng dữ liệu.

### 1.3 Lưu trữ

Mọi bảng giữ object đều ghi **byte thật** (media-storage quy tắc 3):

```text
$ psql … information_schema.columns (cột *_key / *bytes / byte_count)
citizen_photo        object_key, thumbnail_key, byte_count, thumbnail_bytes   → bucket luxmap-citizen
repair_evidence      object_key, thumbnail_key, byte_count, thumbnail_bytes   → luxmap-evidence
work_order_pole_photo object_key, thumbnail_key, byte_count, thumbnail_bytes  → luxmap-evidence
survey_frame         object_key, thumbnail_key, byte_count, thumbnail_bytes   → luxmap-survey
survey_video_clip    object_key, byte_count                                   → luxmap-video
survey_raw_file      object_key, byte_count                                   → luxmap-video
```

Đối chiếu DB với MinIO trên dev — **khớp**:

```text
DB:    repair_evidence 14 dòng, 12.111.073 B · work_order_pole_photo 1 dòng, 1.557.576 B   → 30 object, 13.668.649 B ≈ 13,0 MiB
MinIO: $ mc du --depth 2   →  13MiB  30 objects  luxmap-evidence   (survey / video / citizen: 0)
DB:    pg_database_size('luxmap_dev') = 56 MB
```

Thiếu:

- **`IObjectStore` không có list và không có delete** (`StoreStreamAsync`, `StoreImageAsync`, `OpenAsync`, `ExistsAsync`). Đối chiếu object mồ
  côi cần list; xoá ảnh công dân bị bác (nợ BE-26) cần delete.
- **Không có nguồn "còn trống bao nhiêu".** S3 API không trả dung lượng trống. Trên VPS mọi thứ chung **một đĩa 40 GB**: volume Postgres,
  MinIO, log API, thư mục frame tạm (`SurveyFrameOptions.TempRoot` trong container), image Docker, và **backup** `/var/backups/luxmap`.
  OPS-SIZING dự trù **≥ 160 GB** cho 16 đêm × 30 phút. Đây là rủi ro thật, sớm hơn W16.
- Đo trên dev: `docker exec luxmap_minio df -B1 /data` → `/dev/vda1 977843695616 26618597376 901477875712 3%` — volume Docker báo **đĩa
  chứa nó** (ở dev là đĩa VM của Docker Desktop). Tức API trong container gọi `statfs` trên volume `api_logs` (`/app/logs`) là đọc được đĩa
  chung của VPS, không cần quyền gì thêm.

## 2. Đề xuất

### 2.1 Một endpoint đọc trạng thái

```text
GET /api/v1/admin/system/status          capability mới MonitorSystem = [system_admin]
{
  "generated_at": "…Z",
  "jobs": [ { "name", "state": ok|failing|stalled|running, "last_started_at", "last_finished_at",
              "next_run_at", "last_error", "last_failed_at", "consecutive_failures", "run_count" } ],
  "survey_processing": {
    "by_status": { "queued": n, "processing": n, "failed": n, … },     # processing_status
    "stuck": n,                                                         # processing + lease hết hạn
    "recent_failures": [ { "sweep_id", "attempt", "error_code", "stage", "finished_at" } ]   # 20 run lỗi mới nhất
  },
  "storage": {
    "disk":     { "total_bytes", "free_bytes", "free_ratio", "low": bool },   # statfs Monitoring:DiskPath
    "database_bytes": n,                                                     # pg_database_size
    "buckets":  [ { "bucket", "object_count", "bytes" } ],                   # cộng từ các bảng ở 1.3
    "reconciliation": { "checked_at", "orphan_objects", "orphan_bytes", "missing_objects" } | null
  }
}
```

- `state`: `failing` = lần kết thúc gần nhất là lỗi; `stalled` = `next_run_at` quá `Jobs:PollSeconds + lease` mà không ai giữ lease;
  `running` = đang giữ lease còn hạn.
- `buckets` lấy từ **DB** (rẻ, đúng với dữ liệu có dòng); số "thật" của object store chỉ có ở lượt đối chiếu (2.3).
- Hệ thống toàn cục, **không chia theo xã** (Quản trị có `["*"]`).

### 2.2 Lược đồ (một migration nhỏ)

`scheduled_job` thêm `last_failed_at timestamptz NULL` và `consecutive_failures integer NOT NULL DEFAULT 0` (CHECK `>= 0`); `FailAsync` tăng,
`CompleteAsync` về 0. Không bảng lịch sử từng lượt chạy (log Serilog đã có từng lần lỗi kèm correlation).

### 2.3 Đối chiếu object mồ côi — job `storage_reconciliation` (ngày một lần)

- Thêm `ListAsync(bucket)` vào `IObjectStore` (ListObjectsV2, phân trang). Mỗi bucket: tập key trong store so với tập key ở các bảng 1.3.
- **Mồ côi** = object không có dòng nào, **cũ hơn 24 h** (ghi object trước, commit dòng sau — upload đang chạy trông y như mồ côi).
  **Thiếu** = dòng trỏ tới object không còn (lỗi nặng hơn: người dùng thấy 404).
- **Chỉ báo cáo, không xoá.** Lưu kết quả lần gần nhất vào một bảng nhỏ `storage_reconciliation` (một dòng mỗi bucket, ghi đè).
- So key bằng tập hợp, không sắp theo key (media-storage: không bao giờ sắp theo object key).

### 2.4 Cảnh báo

Job `storage_capacity` (15 phút): `free_ratio < Monitoring:LowDiskRatio` (mặc định 0,15) → thông báo type mới `storage_low` tới mọi
`system_admin`, **một lần mỗi lần rơi xuống ngưỡng** (unique theo đợt, khuôn BE-26 D-5); lên lại trên ngưỡng thì đóng đợt.
Job `failing` / `stalled` **không** tự báo: worker chết thì job báo cũng chết theo — chỗ đó cần giám sát ngoài (cron trên VPS, D-8).

### 2.5 Ranh giới module

Admin không tham chiếu Survey / WorkOrders / Citizen. Port **`IStoredObjectSource`** khai ở `LuxMap.Persistence` (cạnh `IScheduledJob`):
mỗi module sở hữu bảng ảnh tự hiện thực (bucket, đếm, cộng byte, liệt kê key) và đăng ký DI; Admin gom. Chốt chặn: test đọc
`information_schema` mọi cột `*object_key` / `*thumbnail_key` và đỏ khi có cột chưa nguồn nào khai — bảng ảnh mới không lọt khỏi số liệu.
